# ========== 1. 讨论文档 v0.4 ==========

AI辅助创新创造研究系统
讨论文档（持续追加）
版本：v0.4 | 创建日期：2026-10-22
1. 愿景与背景
随着AI快速进化，人类将从繁复重复执行中解放出来，转而追求更多意义与创造。创造与研发本身将从少数人特权变为可规模化的大产业。
目标系统定位：高度AI辅助的创新创造研究平台，促进人人、人机、机机深度协作，把创造效率提升一个数量级，最终形成可交易、可复利的产业基础设施。
核心判断：稀缺资源从“会做”转向“知道做什么、为什么做、如何验证、如何组合”。系统要解决的是创造流程的操作系统问题，而非单纯模型能力。
2. 核心能力框架
2.1 意图层与目标对齐
把模糊意图转化为可计算的目标树、约束与成功标准
支持多人对同一意图的持续对齐与演化
效率杠杆：避免无效探索，让AI与协作者始终围绕同一目标
2.2 多主体协作协议
人-人：实时/异步共创、角色分工、贡献记录
人-机：AI作为可调度的专业代理
机-机：多代理自主分解、并行探索、结果合并与自我验证
效率杠杆：单人线性探索变为并行多路径探索
2.3 知识与组件可组合性
语义化知识图谱 + 资产库
组件具备清晰接口、版本、许可证与使用效果数据
效率杠杆：从零开始变为组合与微调
2.4 快速仿真、原型与验证闭环
多模态生成 + 数字孪生/轻量仿真
自动化实验设计与结果分析
效率杠杆：想法到可测试结果周期从周/月压缩到小时/天
2.5 贡献追踪、激励与价值分配
细粒度贡献记录与可配置分配机制
跨项目声誉与信用积累
效率杠杆：让专业贡献者愿意开放能力，形成正循环
2.6 持续学习与市场化接口
经验自动沉淀为可复用模式
资产发布、交易、交付与外部资源连接
3. 与当前大模型厂商的差异化
大模型厂商卖的是通用能力与接口；本系统卖的是创造流程的操作系统与协作网络。壁垒不在模型本身，而在意图管理、协作协议、知识组合与验证闭环。

4. 三大场景细化
4.1 产品创新
核心痛点
想法多但验证慢，跨职能对齐成本高，已有经验难以复用
针对性能力深化
意图树作为一等公民：商业目标、用户问题、约束（成本/技术/合规/时间）结构化并可版本化。所有代理与组件检索围绕同一棵树工作，支持多人同时修改不同分支并自动检测冲突。
已验证功能模块市场：模块不仅包含代码/设计，还附带使用数据、效果指标、适用场景与约束。系统可根据当前意图自动推荐并生成集成方案。
多角色协作状态机：产品定义 → 交互原型 → 技术实现 → 增长验证，每个阶段有明确完成条件与权限。AI在阶段内推进，关键决策点需对应角色确认。
原生验证闭环：原型生成后直接挂载用户测试或模拟用户代理，反馈结构化回流到意图树对应节点。
差异化壁垒
相比 Cursor / Claude Projects / ChatGPT Canvas：这些工具核心是更快生成与管理上下文，缺乏持续意图对齐、跨角色状态协议、带效果数据的组件复用，以及结构化反馈回流。壁垒来自数据积累——模块效果数据越准，推荐越准。
最小可行范围建议
先聚焦单一垂直品类（如SaaS工具或消费级App）
优先实现：意图树 schema + 版本化、模块元数据、协作状态机
4.2 科研
核心痛点
文献爆炸、假设生成难、实验设计与复现成本高、跨学科协作门槛高
针对性能力深化
假设与证据图谱化管理：每个假设关联支持/反对证据、置信度、可证伪条件与相关实验。多代理可针对同一假设持续辩论并更新置信度。
可复现实验流水线：实验设计、参数、代码、数据、环境自动打包，支持一键重跑或fork修改。贡献精确到具体步骤。
跨实验室资产复用：数据集、预处理流程、评估指标、失败实验记录可检索与引用，系统追踪引用关系。
文献与知识图谱深度融合：支持因果链、矛盾点、未解决空白检索，而非单纯关键词。
差异化壁垒
相比通用文献助手或AI Scientist演示：后者多为一次性生成。本系统壁垒在于长期积累的结构化实验知识、可复现流水线与贡献归属。需要与真实实验流程深度绑定，大模型厂商难以深入。
4.3 硬件
核心痛点
设计-仿真-制造周期长、物理约束强、供应链与成本敏感、迭代成本高
针对性能力深化
约束优先的设计生成：先定义功能、成本上限、可制造工艺、供应链偏好、合规要求，再在硬约束下搜索设计空间。
多工具仿真编排：对接现有工具（结构/热：FreeCAD+开源求解器；PCB：KiCad；流体：OpenFOAM等），系统负责参数化、批量仿真、结果对比与统一回流。
仿真-实测闭环：打样实测数据上传后自动对比偏差，建议修正模型参数，长期积累特定工艺/材料的偏差模型。
供应链与成本实时约束：设计变更时自动估算对BOM、交期、成本的影响。
差异化壁垒
硬件是大模型最难直接覆盖的场景。壁垒来自约束模型准确性、多工具编排稳定性，以及仿真-实测偏差数据的积累。这些需要与真实硬件团队长期合作打磨。
建议切入点
先聚焦单一子领域（如消费电子结构件或简单IoT设备）
5. 技术架构
采用分层 + 可插拔架构，底座统一，领域能力以插件/代理形式扩展。三个场景共享意图层、知识图谱、协作协议与贡献追踪。
5.1 核心数据层
知识图谱（Neo4j或开源替代）：存储意图、实体、关系、组件、贡献、实验结果。节点类型含Intent、Hypothesis、Component、Agent、Contribution、Experiment、Constraint等，支持时间版本与置信度。
向量与多模态索引：文档、代码、设计文件、仿真结果嵌入，支持图+向量混合查询。
对象存储 + 版本控制：代码、设计、仿真数据、实验记录。
5.2 意图与协作层
Intent Engine：自然语言/多模态输入转化为结构化意图树，支持持续更新与多人对齐。
协作协议：状态机（Draft → Exploring → Validating → Committed）、权限模型、冲突检测与合并规则。
贡献追踪：细粒度记录动作来源、时间、影响范围。
5.3 多代理执行层
Agent Framework：研究、设计、仿真、批判、编排等代理类型，支持工具调用与互相通信。
编排与调度：根据意图与状态动态调度，支持人机混合决策点。
5.4 领域能力插件与反馈层
产品创新插件：原型生成、用户测试编排、增长模型模拟。
科研插件：文献图谱、假设生成、实验设计、可复现流水线。
硬件插件：多物理场仿真接口、设计生成、供应链匹配。
所有验证结果自动回流更新知识图谱与代理策略。
5.5 技术选型建议
图数据库：Neo4j / Memgraph
向量检索：Milvus / Qdrant 或与图库结合
多代理：基于AutoGen、CrewAI、LangGraph或自研状态机，重点做贡献追踪与权限
仿真接口：优先对接开源工具（OpenFOAM、FreeCAD、KiCad）+ 商业工具API
5.6 任务管理系统（树状结构 + 调度）
任务系统是意图树、假设/方案与实际执行之间的桥梁。采用树状结构，可对应不同假设验证方案、产品验证路径或硬件测试计划，并支持调度AI代理或人类执行。
核心设计
树状任务结构：根节点对应高层意图或假设，子节点为分解后的验证步骤、实验、原型任务、仿真运行等。支持多分支并行（不同验证方案同时推进）。
与假设/方案的直接映射：每个主要分支可绑定一个假设、产品形态或设计方案，任务完成状态与结果自动更新对应假设的置信度或方案可行性。
执行者调度：任务可指定执行者类型（特定AI代理、代理池、人类角色、或混合）。系统根据任务属性（复杂度、需要物理操作、需要判断等）自动推荐或自动分配。
状态与依赖：支持前置依赖、并行、条件分支。任务状态（待分配、进行中、待审核、完成、失败）与贡献记录联动。
结果回流：任务产出（数据、代码、报告、仿真结果）自动关联到知识图谱对应节点，并触发下游任务或假设更新。
在三个场景中的作用
产品创新：一个产品意图下可并行多个验证方案（不同交互、不同定价），每个方案下挂载原型生成、用户测试、数据分析等任务，由AI或人类执行。
科研：每个假设对应一棵验证任务树（文献补充、实验设计、仿真预跑、实际实验、数据分析），支持多代理辩论后自动生成或调整任务。
硬件：设计方案下挂载仿真任务、参数扫描、供应链询价、打样任务等，仿真类可全自动由AI调度工具执行，物理打样则调度人类或外部服务。
与现有架构的关系
任务树存储在知识图谱中，与Intent、Hypothesis、Component节点关联。
多代理编排层直接消费任务树进行调度与执行。
协作协议中的权限与贡献追踪覆盖任务执行全过程。
是把“想法/假设”转化为“可调度工作”的关键机制，补齐从规划到执行的闭环。
5.7 可沉淀可复用资产管理系统与空间设计
资产系统负责把创造过程中产生的知识、组件、实验、设计、失败案例等沉淀为可检索、可组合、可交易的资产。个人空间、团队空间、项目空间是资产的组织与权限边界。
资产管理系统设计
资产类型：组件（代码/设计/模型）、实验流水线、假设与证据包、设计约束与仿真结果、失败案例、数据与预处理流程、提示与代理配置等。
核心元数据：语义描述、适用场景与约束、版本、许可证、贡献者、使用效果数据（成功率、节省时间、引用次数）、依赖关系。
沉淀机制：项目或任务完成时，系统自动或半自动提示可沉淀资产；支持人工标注与质量评级。
复用方式：语义检索 + 图关系推荐；支持“以结果为导向”搜索（类似约束下的类似问题）；一键fork或组合到新项目。
权限与交易：资产可设为私有、团队内、公开；公开资产支持引用追踪与收益分成。
存储：核心关系在知识图谱，大文件在对象存储，向量索引支持语义检索。
个人空间
私有工作区：个人草稿、未发布资产、个人代理配置、学习笔记。
个人资产库：用户主动沉淀的可复用组件与经验，可选择分享到团队或公开。
能力画像：系统根据贡献与使用记录生成个人专长标签，便于协作匹配。
权限：完全私有，可选择性授权给特定项目或团队。
团队空间
共享资产库：团队内部验证过的组件、流程、模板、失败案例，默认对团队成员可见。
协作规范：团队级意图模板、角色定义、贡献分配规则。
权限模型：管理员、编辑者、查看者；支持子组或项目级更细权限。
跨项目复用：团队资产可被多个项目直接引用，引用关系可追踪。
项目空间
项目是意图树 + 任务树 + 临时资产的容器。
项目内资产：当前项目产生的草稿、中间结果、实验数据，默认项目成员可见。
外部资产引用：可从个人空间、团队空间或公开市场引用资产，引用时记录版本与依赖。
沉淀出口：项目结束或里程碑时，可将高质量资产一键沉淀到团队空间或个人空间，并标记来源项目。
权限与生命周期：项目可设为私有、团队内或公开；结束后可归档，资产仍可被后续项目复用。
三者关系与流转
个人空间 → 项目空间（贡献草稿与私有资产）→ 团队空间（沉淀验证后的资产）→ 公开市场（可选）。反向：公开/团队资产可被任意项目引用。知识图谱维护所有引用、版本与贡献关系，确保可追溯。
5.8 经济系统设计
经济系统把贡献计量、价值分配与收益变现连接起来，让创造从成本中心变成可交易网络。它依赖贡献追踪、资产系统与空间权限作为基础。
核心机制
贡献计量：基于任务执行、资产贡献、决策影响、引用次数等细粒度记录，形成可计算的贡献分。
内部激励：积分/声誉系统。积分可用于兑换算力、优先调度、高级功能；声誉影响协作匹配与项目邀请权重。
资产收益：公开资产被引用或购买时，按贡献比例或设定规则向贡献者分成。支持一次性许可、订阅或按使用付费。
项目收益分配：项目商业化后（产品上线、科研成果转化、硬件量产），可按预先约定的贡献比例或动态规则分配收益。
平台抽成：对资产交易、项目收益分成收取一定比例，作为平台主要收入来源之一。
外部价值连接：支持对接外部支付、股权工具或基金，便于真实货币结算或投资。
在三个场景中的体现
产品创新：成功产品的收益按贡献分配；高复用组件可在市场持续产生许可收入。
科研：实验流水线、数据集、失败案例被引用时产生分成；科研成果转化时可分配收益。
硬件：设计方案、仿真模型、工艺know-how被复用或授权时产生收益；量产项目可按贡献分配。
设计原则
透明可审计：所有分配规则与记录可查询，减少纠纷。
灵活可配置：项目或资产可自定义分配规则（固定比例、按贡献动态、阶梯等）。
低门槛启动：早期可用积分与声誉驱动，后期逐步引入真实货币。
与贡献追踪强绑定：经济分配必须以已记录的贡献为依据，避免主观扯皮。
与现有系统的关系
贡献追踪提供计量基础；资产系统提供可交易对象；空间权限决定可见与可交易范围；任务系统记录执行贡献。经济层是这些机制的价值出口。
6. 落地节奏与当前结论
建议优先级
产品创新作为首个突破口：验证最快，最容易积累可组合模块数据。
科研作为第二曲线：重点打可复现流水线与假设管理。
硬件周期最长、集成最重，建议在前两个场景有一定用户与数据后再重点投入，或先聚焦子领域。
任务管理系统建议在意图层与多代理编排之后尽快落地，作为执行调度的统一入口。
资产系统与空间设计建议与任务系统同步规划，优先实现项目空间内的资产沉淀与团队空间复用。
经济系统可在资产与贡献追踪稳定后逐步引入，先用积分与声誉，再开放真实收益分配。
当前核心结论（v0.4）
系统定位是创造流程的操作系统，而非通用模型能力层。
差异化壁垒建立在意图管理、协作协议、可组合资产积累与领域验证闭环上。
三个场景共享底座，差异在代理类型、工具接口与验证方式。
大模型作为能力层调用，不正面竞争模型性能。
经济与激励层（贡献追踪 + 价值分配）是形成网络效应的关键。
树状任务管理系统是必要组件：它把假设/方案转化为可调度的工作单元，支持AI与人类混合执行，并与验证结果闭环联动。
可沉淀可复用资产系统 + 个人/团队/项目空间是复利的基础：项目产生资产，团队积累资产，个人保留私有能力，公开市场形成交易网络。
经济系统通过贡献计量、积分声誉、资产分成与项目收益分配，把协作网络转化为可持续的价值创造与分配机制。

## 1. 产品定位

### 1.1 一句话

**InnoForge** 是创造流程的操作系统：把模糊意图变成可对齐的目标树、可调度的项目任务、可验证的闭环，以及可沉淀复利的资产网络；大模型只是能力层，壁垒在流程、协作协议与资产积累。

### 1.2 卖什么 / 不卖什么

| 卖 | 不卖（非目标） |
|----|----------------|
| 意图对齐与版本化目标树 | 通用大模型本身的性能竞赛 |
| 多主体协作协议（人-人 / 人-机 / 机-机） | 又一个「聊天式项目空间」 |
| 项目内任务树 → 验证 → 回流 | 独立的个人待办 / 工单产品 |
| 可组合资产 + 个人/团队/项目空间边界 | 一上来就做真钱市场与完整图谱库 |
| Credit / 声誉 /（远期）分成激励 | 用新经济叙事覆盖 Intent OS Credit 闭环 |
| 三场景共享底座、插件差异 | 拆成三个独立产品 |

### 1.3 与 Intent OS × InnoForge 的关系

- **Intent OS 闭环保留**：创建意图（质押）→ 孪生 / Agent 判断 → 人类确认 → 受控部署 → 反馈结算 → 权益 / 声誉。  
- **v0.4 叠加为同一产品的上层能力地图**：项目容器、意图树、项目任务树、空间权限、资产沉淀、场景插件 — **映射进闭环，不另起产品、不覆盖 Credit / 部署 / 治理**。  
- 现行原型中的「意图（intent）」在产品层升格为 **项目（Project）的主意图载体**（见 §2）；技术上可暂用 `forge_intents` 承载，但产品语义以项目为准。

## 2. 核心对象模型

### 2.1 对象一览

| 对象 | 定义 | 归属 |
|------|------|------|
| **Team** | 组织 / 协作单元；共享规范与团队资产库 | 租户下 |
| **Project** | **创造工作的主容器**：意图树 + 任务树 + 项目内临时资产 + 成员与权限 + 场景模式 | 属于 Team（或个人临时团队） |
| **Intent tree** | 项目内目标 / 约束 / 成功标准 / 分支的可版本化树 | **仅存在于 Project** |
| **Task tree** | 把假设 / 方案 / 验证路径拆成可调度工作单元（AI \| HUMAN \| 混合） | **仅存在于 Project**；可绑定意图树节点 |
| **Collab stage** | 项目级协作状态机（如 Draft → Exploring → Validating → Committed） | Project |
| **Space** | **权限与资产边界**，不是第二套任务系统：Personal / Team / Project | 见 §2.3 |
| **Asset** | 可沉淀组件、实验包、设计、失败案例等 | 产生于 Project；可沉淀到 Personal / Team / 公开市场 |
| **Contribution** | 细粒度动作与影响记录（任务执行、判断、资产、决策） | 贯穿 Project；汇总到个人声誉 |
| **Credit / 经济** | Intent OS 质押与结算 + 远期积分声誉 / 资产分成 | 不因 v0.4 被替换 |

### 2.2 关键关系（产品层）

```
Team
 └─ Project  ←—————— 主容器（随项目走）
      ├─ Intent tree     （对齐「做什么 / 为何 / 成功标准」）
      ├─ Task tree       （对齐「谁执行 / 做到哪 / 结果回流」）
      ├─ Collab stage + agents
      ├─ Project-space assets（草稿、中间结果）
      └─ Deploy / validate / feedback（接 Intent OS 确认·部署·结算）

Personal space
 └─ 私有资产 · 草稿 · 代理配置
 └─ 「我的任务」= Σ(各 Project 中 assigned-to-me 的任务)   ← 视图，非第二任务库

Team space
 └─ 已验证共享资产 · 模板 · 分配规则

Public market（远期）
 └─ 公开资产交易 / 引用分成
```

### 2.3 空间：权限与资产边界（不是任务空间）

讨论文档 §5.7：**个人 / 团队 / 项目空间是资产的组织与权限边界**。

| 空间 | 装什么 | 不装什么 |
|------|--------|----------|
| **Project space** | 本项目意图树、任务树、中间产物、实验数据；成员可见 | — |
| **Team space** | 团队验证过的组件、流程、模板、失败案例 | 独立任务队列 |
| **Personal space** | 私有草稿、未发布资产、个人代理配置、能力画像 | **独立任务系统** |

**「我的任务」**：产品入口可以存在（总览或个人空间附属），但语义是：

> 跨项目过滤视图：`WHERE assignee = me AND project.status ∈ active`

任务的创建、分解、依赖、完成、结果回流 **一律在所属 Project 内完成**。个人视图禁止成为可脱离项目的任务 CRUD 主路径。

### 2.4 意图树 vs 任务树

| | Intent tree | Task tree |
|--|-------------|-----------|
| 回答 | 目标对齐了吗？约束/成功标准是什么？ | 谁去做？做到哪一步？产出是什么？ |
| 节点例 | GOAL / CONSTRAINT / SUCCESS / BRANCH（假设或方案） | 验证步骤、原型、实验、仿真、打样、评审 |
| 绑定 | — | 任务可绑定意图节点（尤其 BRANCH / SUCCESS） |
| 回流 | 验证结果更新节点状态 / 置信度 | 任务 DONE/FAILED 触发回流与下游任务 |

### 2.5 与 Intent OS 对象的映射（整合，不覆盖）

| Intent OS / 现行 InnoForge | 产品方案中的位置 |
|----------------------------|------------------|
| Intent + stake / Credit | Project 创建与资源承诺；Credit 账本不变 |
| Constraints / freeze | Intent tree 的 CONSTRAINT + 冻结规则 |
| Twin / Agent variants / judgments (G2) | 工作台确认层；判断写入责任链与贡献 |
| Confirm → Deploy → Feedback → Settle | 项目验证与物理执行出口；阶段 Committed ≠ 已部署 |
| Snapshots / governance (G6) | 项目版本与回滚 |
| Lifeforms (G7) | 结算后可选演化；仍挂在项目脉络 |
| Lumen memories (G8) | 个人/项目记忆；可沉淀为资产候选 |
| Reputation / allocations (G4/G5) | 贡献出口；任务执行为新增贡献源 |
| Marketplace / adapters | 资产复用与外部能力；接 Team / Public |

## 4. 产品信息架构（流程，非像素）

### 4.1 主流程（创造闭环）

```
创建 / 加入 Project（场景 · 成员 · Credit 质押若需要）
  → 对齐 Intent tree（多人分支 · 冲突提示 · 版本）
  → 协作阶段推进（代理在场 · 关键人类确认）
  → 在 Project 内展开 Task tree（绑定意图节点 · 分配 AI|人）
  → 执行与评审 → 结果回流意图树 / 假设置信度
  → 验证出口：确认调度 · 部署 · 反馈 ·（可选）生命体
  → 里程碑：资产沉淀提示 → Personal / Team /（远期）市场
  → 贡献计量 → Credit 结算 / 声誉 /（远期）分成
```

### 4.2 导航语义（产品层 IA — 纠正 F1）

产品层应以 **Project 为中心**，而不是「顶层并列任务空间 + 顶层并列资产三栏」：

| 区域 | 产品含义 | 正确 / 错误 |
|------|----------|-------------|
| 项目上下文壳 | 当前 Project：意图树 · 协作 · **项目任务** · 工作台 · 部署 | ✅ 任务在此 |
| 发现 / 项目列表 | 进入或创建 Project | ✅ |
| 个人「我的任务」 | 跨项目 assignment 视图 | ✅ 仅视图 |
| 个人 / 团队空间 | 资产与权限 | ✅ 非任务库 |
| **顶层并列「任务执行」与「资产空间」对等、暗示独立任务空间** | F1 壳层产品表述 | ❌ **产品错误，须在后续 UI 设计废止** |

### 4.3 空间流转（产品）

`个人草稿 → 项目内使用 → 里程碑沉淀到团队 → 可选公开市场`  
反向：`市场 / 团队资产 → 引用进项目（记版本与依赖）`。

## 7. F1 产品错误（显式废止）

F1 实现把侧栏做成对等分组「任务执行 | 资产空间」，并提供顶层 Tasks / Spaces 页，容易读成：

- 存在与项目平级的「任务空间」；  
- 个人 / 团队 / 项目是并列任务或工作区，而非 **资产权限边界**；  
- 「我的任务」可以脱离项目存在。

**废止结论（产品层）：**

1. 不存在独立的「任务空间」产品概念。  
2. Task tree **只**属于 Project；随项目归档/生命周期。  
3. Personal「任务」= 跨项目 assignments 视图。  
4. Spaces = 资产与权限；Project space 与 Project 容器同体，不是第四套任务箱。  
5. 后续 UI 设计必须以 Project 为导航中心重排 IA；F1 代码可暂留，但不得再按错误模型扩展产品叙事。

详见 [fidelity plan · F1 纠错](./innoforge-v04-ui-fidelity-plan.md)。

# InnoForge × Intent OS 产品设计（现行）

**版本**：v1.8-living  
**日期**：2026-10-23

## 1. 整合原则（必须遵守）

1. **不丢弃 Intent OS**：意图创建、数字孪生、Agent 采纳/拒绝、Credit 质押与兑现、发现参与、确认调度、判断历史与权益归因，全部保留为闭环一等环节。  
2. **叠加 InnoForge**：工作台意图卡片与 Lumen、多角色协商、具身协作画布、制造参数、受控物理部署、生命体演化、治理审批与审计，作为同一闭环的延伸层。  
3. **叠加 v0.4 研究系统愿景**：六大能力、三场景（产品/科研/硬件）、分层架构、任务树、资产空间与经济系统作为**同一操作系统的上层能力地图**，映射到现有闭环，不另起产品。  
4. **一条闭环，一个产品**：数字意图 → 多代理协作确认 → 受控物理部署 → 治理与反馈 → 价值兑现 / 生命体演化。  
5. **经济双轨并存（原型）**：Credit 质押/铸造/分配（Intent OS）与订阅/打样计费叙事（InnoForge）并存；v0.4 积分/声誉/资产分成是同一激励层的远期扩展。

---

## 2. 一句话定位

**InnoForge** 是承载 Intent OS 的**创造流程操作系统**与受控物理执行网关：让人类意图可见、可协商、可确认，并可在确认后进入制造与反馈；壁垒在意图管理、协作协议、可组合资产与验证闭环，而非通用模型能力本身。

## 3. 完整闭环（整合）

```
创建意图（Credit 质押 · 场景模式）
  → 意图树对齐（目标 / 约束 / 成功标准 · 版本）
  → 工作台 / 孪生（意图卡片 · Lumen · Agent/变体采纳拒绝）
  → 协作画布（阶段状态机 · 多角色协商 · 裁决入责任链）
  → 可制造参数与确认调度（人类确认后才消耗资源）
  → 治理审批 · 部署执行 · 现实反馈
  → 生命体演化提案（可选）
  → 真实价值兑现（Credit 铸造与归因分配）
  → 发现与异步再参与 · 资产沉淀（远期）
```

| 环节 | Intent OS 来源 | InnoForge 来源 | v0.4 叠加 | 原型界面 |
|------|----------------|----------------|-----------|----------|
| 个人总览 | 意图库、Credit、声誉、权益预览 | — | 场景模式切换 | 总览 |
| 创建意图 | 意图定义、约束、Credit 质押 | 垂直模板 | 场景种子（产品/科研/硬件） | 创建意图 |
| 意图对齐 | 约束边界 | — | **意图树一等公民** | **意图树** |
| 展开与确认 | 孪生、Agent 候选采纳/拒绝 | 意图卡片、变体、Lumen | 树节点回流 | 工作台 |
| 多角色协作 | 异步判断接力 | Collaborative、协商、具身 | **协作阶段状态机** | 协作 |
| 发现参与 | 发现项目、质押、潜在权益 | 项目 / 生命体 | 资产市场入口（远期） | 发现 |

# ========== 5. 外部系统版图 ==========

# InnoForge 外部系统版图

**原则**：物理 AI 不只「自己对接一台设备」，而是通过**统一执行网关 + 可插拔适配器**对接一整类相关外部系统。当前一律 **接口占位 + 模拟实现**；有真实凭证时再切换 Provider。

## 为什么要多系统

闭环是：意图 → 协商确认 → **物理执行与供应链** → 反馈 → 兑现。  
数字侧需要模型/工具/身份；物理侧需要制造、物流、传感；商业侧需要支付与合规。系统必须可扩展对接，而不是写死一家厂商。

---

## 1. 物理执行与制造

| 系统类型 | 做什么 | 示例形态 |
|----------|--------|----------|
| CNC / 机床控制 | 下发刀具路径、工单、状态回传 | 厂商 OPC-UA / MTConnect / 私有 API |
| 3D 打印 / 增材 | 切片任务、材料、打印队列 | OctoPrint、Bambu、厂商云 |
| 打样 / 柔性制造平台 | 小批量下单、报价、交期 | 第三方 fab API |
| MES / 工单系统 | 工单、工序、在制 | 工厂 MES |
| 机器人 / 机械臂 | 抓取、装配、产线节拍 | ROS 2、厂商 SDK |
| IoT / 传感与边缘 | 温振、视觉质检、设备心跳 | MQTT、边缘网关 |
| 数字孪生 / PLM·CAD | 几何与 BOM、版本、DFM | CAD/PLM 导出、STEP/GLTF |

**原型**：`partner-http` + 本地 webhook 仿真接收器（接口占位）；注册表 `mfg-*`。

---

## 2. 供应链与履约

| 系统类型 | 做什么 |
|----------|--------|
| 原材料 / 零部件供应 | 询价、库存、交期 |
| 物流与仓储（WMS/TMS） | 发货、追踪、入库 |
| ERP | 订单、成本、库存主数据 |
| 质量 / 实验室（QMS） | 检验结果回写意图与生命体 |

**原型**：Deploy 进度与供应链信号用模拟事件；`sc-*` Simulator。

## 3. 智能与工具（数字侧）

| 系统类型 | 做什么 |
|----------|--------|
| 大模型 / Agent 运行时 | 变体生成、协商代理、Lumen |
| 向量 / 记忆存储 | 伙伴长期记忆、项目共识 |
| 仿真与有限元 / DFM | 可制造性与强度预检 |
| 代码与 CI（可选） | 固件/控制脚本发布到边缘 |

**原型**：本地 mock Agent；记忆存本地/云端快照；`intel-*`。

## 4. 身份、协作与治理

|----------|--------|

## 6. 运行与观测

| 系统类型 | 做什么 |
|----------|--------|
| 对象存储 | 模型、切片、审计附件 |
| 密钥管理（KMS） | 厂商密钥与 webhook 签名 |
| 可观测性 | 任务与适配器延迟/失败 |

---

## 对接架构（约定）

```
InnoForge 核心闭环
    └── 受控物理执行网关（统一任务 / 审批 / 回写）
            └── External Adapter Registry（统一合同）
                    ├── manufacturing: CNC / 打印 / 打样 / MES / 机器人 / IoT / 孪生
                    ├── supply_chain: 供应 / 物流 / ERP / QMS
                    ├── intelligence: LLM / 记忆 / DFM / CI
                    ├── identity: IdP / SCIM / SIEM / 通知
                    ├── commerce: 支付 / 税务 / 市场目录 / 账本
                    └── observability: 对象存储 / KMS / OTel / Secrets
```

每个 Adapter：**同一接口**（createJob、getJob、cancelJob、health、可选 tick）+ **Simulator 实现**（默认）+ **Real 实现**（有凭证时启用，如 `STRIPE_SECRET_KEY`、`EXTERNAL_FAB_REAL`）。

人类主权不变：进入真实外部系统前仍经 Governance 确认。

## 与代码的对应（当前）

# ========== 6. Intent OS 产品方案（源） ==========

# Intent OS 产品方案文档
## 人类意图操作系统

**版本**：v1.0  
**日期**：2026-10-15  

---

## 1. 产品定位

**一句话定位**  
AI时代人类意图的操作系统。

**愿景**  
在重复劳动被AI大量承接之后，让人的判断、取舍与意义赋予能够被低摩擦地展开、协作、实现，并获得与其独特影响相匹配的回报。

**核心问题**  
有意义的意图和判断难以被准确共享、持续演化、低摩擦实现，并在真实价值兑现时公平回报给真正产生影响的人。

---

## 2. 产品原则

1. **意图可见优先**：意图与关键取舍是一等公民。
2. **提议与确认分离**：Agent可大量生成候选，改变方向或消耗资源必须由人确认。
3. **归因到判断而非操作**：权益基于对方向的独特影响。
4. **孪生作为唯一协作界面**：所有协作围绕共享数字孪生展开。
5. **异步共创友好**：支持不同时间的有效判断接力。
6. **实现为可选延伸**：数字探索本身具有价值，物理实现是确认后的升级。
7. **权益与独特影响绑定**：回报向影响方向的人类判断倾斜。
8. **表达有成本**：通过Credit质押约束低质量表达。
9. **履约收益显著高于违约**：强激励合作与守约。
10. **降低协作心理成本**：让高质量判断的供给变得轻量。

---

## 3. 核心概念

- **数字孪生**：共享事实源，承载意图、约束、版本、贡献归因与执行反馈。
- **判断贡献**：定义、选择、否决、确认、意义澄清等对方向产生独特影响的行为。
- **Credit**：仅在真实价值兑现时铸造的可交易信用值，用于表达质押与收益分配。
- **提议与确认**：Agent提案与人类确认严格分离。

---

## 4. 系统架构

- **意图层**：目标、约束、意义记录
- **孪生层**：可版本化、可归因的共享模型
- **能力层**：Agent作为展开与候选生成器
- **实现层**：仿真 + 可选物理执行网络（结果回写）
- **价值层**：Credit铸造、质押、差异化分配、履约判定

---

## 5. 经济系统

### Credit机制
- 仅在产生真实订单、订阅、外部调用收益或可验证交付时铸造。
- 表达（创建意图、关键建议、表决、确认执行）需质押Credit。
- 采纳且贡献价值则返还+奖励；无效则损失质押。

### 差异化分配
- 意图提出者：长期追溯权益（高）
- 关键建议者：按采纳影响（中高）
- 表决/确认者：按一致性与责任（中）
- 协作者与验证者：按履约（中）
- 责任承担者：风险溢价（高）

### 激励设计
- 履约获得1.5–3×系数加成。
- 违约削减权益并降低未来信用权重。
- 高度一致的成功协作可放大分配池。
- 早期正确判断可在衍生价值中持续分成。

---

## 6. 主要功能模块

- **个人空间**：意图库、Credit余额与质押、判断声誉、权益预览
- **项目孪生空间**：意图面板、孪生主体、Agent候选（采纳/拒绝）、版本与判断历史
- **贡献与权益**：角色权重、分配预览、追溯权益
- **发现与参与**：异步判断机会、所需质押、潜在权益
- **创建流程**：意图定义、约束设置、Credit质押
- **确认与调度**：锁定版本、资源预期、质押确认后执行

---

## 7. 关键流程

1. 质押Credit创建意图 → 生成初始孪生  
2. Agent生成候选 → 人确认/拒绝 → 归因记录  
3. 异步参与者查看意图历史并贡献判断  
4. （可选）确认后调度物理执行 → 结果回写  
5. 真实价值兑现 → 铸造Credit → 按归因+履约分配  

---

## 8. 商业模式

- 判断权益与长期追溯分成
- 孪生/组件复用调用分成
- 实现即服务（物理调度收费回流贡献者）
- 意图托管
- 反向悬赏（为关键判断付费）

---

## 9. MVP范围

- 单项目孪生（意图+版本+基础归因）
- Credit质押与模拟兑现分配
- Agent候选 + 人工确认
- 基础异步协作与个人总览

## 10. 差异化

区别于Agent聊天工具、传统协作软件和纯制造平台。本产品将**人类判断作为核心生产资料**，以数字孪生统一事实，以Credit约束表达并奖励真实影响，以履约机制强化合作。

# ========== 7. InnoForge 产品设计更新版（源） ==========

# InnoForge 产品设计文档（更新版）
## 物理 AI + 持续创新闭环

**版本**：v1.1  
**日期**：2026-10-17  
**更新说明**：整合商业计划洞察、人机共生五方向、以及从数字到物理的完整闭环要求。

---

## 1. 产品定位

轻量级**创新操作系统 + 受控物理执行网关**。  
以可操作图谱为核心界面，承载意图共生、多角色协商、具身协作、伙伴记忆与创新生命体，并把确认结果通过标准接口推向制造与反馈。

---

## 2. 设计原则

- 可见的共生：AI 有身份、立场、记忆与责任标记。
- 可追溯：所有关键决策可回溯到信号与人类确认。
- 渐进具身：2D 为主，按需进入可操作预览。
- 人类主权：部署、冻结、否决默认需要确认。
- 垂直优先：用模板降低首次价值时间。

---

## 3. 核心闭环与模块映射

| 闭环环节 | 主要模块 | 关键界面 |
|----------|----------|----------|
| 意图与约束 | 意图假设卡片、伙伴记忆 | Workbench 顶部 + Lumen 面板 |
| 共生生成与协商 | Tools、角色代理、协商会话 | 变体网格、Collaborative 画布、协商弹窗 |
| 可制造性与参数 | 制造参数配置、AI 推荐 | Deploy 配置模态 |
| 受控部署 | 部署队列、Governance 审批 | Value / Governance |
| 现实反馈 | 供应链进度、设备反馈、信号 | Deployments 卡片 |
| 持续演化 | 生命体状态、待确认提案 | Lifeforms 面板 |

---

## 4. 五方向产品承载（深化）

### 4.1 意图层共生
- 常驻可编辑意图卡片，支持溯源、修改、冻结。
- 生成结果标注「服务于意图 X」。
- 变体可反向写入意图。

### 4.2 多角色 AI 协商
- 项目可启用 Cost、Experience、Sustainability、Compliance 等代理。
- 冲突或分歧时展开协商会话，代理给出建议 + 影响预估。
- 裁决结果写入责任链；Compliance 可配置否决权。

### 4.3 具身协作空间
- 节点一键具身化，2D/具身模式切换。
- 具身操作（比例、材质、装配）双向同步到参数。
- AI 可在空间中高亮建议，操作轨迹可回放。

### 4.4 长期共生伙伴
- 稳定伙伴身份（如 Lumen），常驻侧边或 Muse。
- 记忆可查看、忘掉、晋升为项目共识。
- 发言带溯源，跨会话引用历史偏好。

### 4.5 创新生命体
- 首次成功部署并收到反馈后可转化为生命体。
- 显示运行实例、最新信号、待确认提案。
- 支持确认演化、拒绝、冻结、终止。
- Discover 中区分生命体与静态项目。

---

## 5. 信息架构与主要视图

1. **Workbench**：意图卡片 + 种子 + 变体网格 + Lumen 对话  
2. **Discover**：项目/生命体列表，支持加入或共生  
3. **Collaborative**：参与者与代理列表 + 可拖拽画布（连线样式）+ 聊天/协商 + 具身切换  
4. **Deploy & Lifeforms**：生命体状态 + 部署列表（供应链/设备进度）+ 组件版本  
5. **Governance**：待审批现实动作 + 审计日志  

辅助：Tools 面板、Rollback、制造参数模态、协商模态、记忆管理模态。

---

## 6. 关键交互规范

- 所有 AI 生成与提案默认带「AI」标记与理由。
- 部署相关动作必须经过 Governance 或明确确认。
- 冲突与协商必须留下裁决记录。
- 支持快照与回滚。
- 移动端侧边栏可折叠，核心操作保持可用。

---

## 7. 数据与责任

- 本地/云端持久化：变体、快照、组件、部署、意图、记忆、审计。
- 责任链字段：操作者（人/AI/代理）、时间、依据信号、确认人。
- 导出能力：审计日志、制造参数包。

---

## 8. 垂直模板示例（第一优先）

**小批量结构件模板**
- 预置材料库（PLA、PETG、铝合金等）
- 常见工艺（FDM、CNC）
- 默认可制造性检查项
- 合作打样商快捷通道

- 试点团队的返工次数下降

本设计直接服务于「垂直闭环优先、可审计共生、轻量网关」的商业路径。所有新增深度功能都围绕提高价值密度与可防御性，而非追求通用覆盖。

# ========== 8. InnoForge 商业计划分析（源） ==========

# InnoForge 商业计划分析文档
## 物理 AI + 持续创新闭环方向

**版本**：v1.0  
**日期**：2026-10-17  
**依据**：前期产品演化、人机共生深度方向、市场与赛道研究（Bain、Gartner、IDC 等）

---

## 1. 执行摘要

InnoForge 定位为**轻量级创新操作系统 + 受控物理执行网关**，聚焦「想法 → 共生决策 → 可制造参数 → 真实反馈 → 持续演化」闭环。  
它不是通用协作工具，也不是重型 PLM 替代品，而是连接数字创新与物理制造的高价值切片。

**核心判断**：
- 赛道空间大（物理 AI / 工业创新是未来万亿级 AI 收入缺口的重要来源）。
- 具体产品近中期现实体量中等（数万团队级），适合「深而贵」路径。
- 成功关键在于垂直闭环做透 + 可审计治理 + 生态连接，而非功能堆砌。

---

## 2. 市场与机会

### 2.1 赛道背景
- AI 总支出已进入万亿级（Gartner 2026 年 $2.5T+）。
- Bain 指出到 2031 年需约 $6T 年收入支撑基建，其中约 $4.2T 必须来自新场景，包括物理 AI、工业自动化、数字孪生与全新产品。
- 工业 AI 目前百亿级，但增速高；AI in PLM 约 $10B 级并向 $20B+ 发展。真正空间在于把创新过程与制造执行打通后的外溢。

### 2.2 目标市场
- **SAM**：有真实原型/小批量制造需求的创新团队与企业 R&D（全球估计数十万团队量级中的可服务部分）。
- **SOM（3–5 年）**：200–2000 个付费团队起步，逐步扩展至数千。
- 优先垂直：小批量消费硬件结构件、可持续包装、教育/医疗原型、企业创新实验室。

### 2.3 竞争格局
- 通用协作（Miro、FigJam、Notion）：停在数字层。
- 重型 PLM（Siemens、Dassault、PTC）：功能全但重、贵、AI 多为附加。
- 生成设计工具：缺协商、责任链与反馈闭环。
- **差异化**：可见的人机共生（意图、多代理协商、伙伴记忆）+ 受控制造网关 + 创新生命体 + 完整审计。

## 3. 产品与价值主张

### 3.1 核心闭环
意图/约束 → 共生生成与协商 → 可制造性校验与参数化 → 受控部署 → 现实反馈回流 → 生命体持续演化。

### 3.2 关键能力
- 意图假设与信号溯源
- 角色化 AI 代理与协商会话
- 具身协作（2D ↔ 可操作预览）
- 长期共生伙伴与记忆管理
- 制造参数配置、供应链/设备反馈
- 创新生命体与待确认提案
- 治理与责任链

### 3.3 用户价值
- 缩短想法到可制造的时间
- 降低返工与材料浪费
- 让 AI 参与决策可接受（可追溯、可否决）
- 把成功方案沉淀为可复用资产

## 4. 商业模式

## 5. 财务情景（保守）

- 付费团队：200–800

- ARPU：$50/人/月

- 付费团队：2000–8000
- ARR 潜力：$15M – $60M+

**关键假设**：垂直标杆成立、制造对接稳定、留存率 >70%、销售周期可控。

### 阶段 3（24 个月+）：生态与扩展
- 跨项目共生与能力市场

## 9. 结论与建议

InnoForge 所代表的方向嵌入在一个巨大的物理 AI 与工业创新空间中，但具体产品必须走垂直、深耕、可交付的路径，才能把赛道潜力转化为现实收入。  
近中期预期应保持谨慎务实；中长期若闭环与生态建立，有机会成为特定制造创新链条上的关键轻量基础设施。

1. 选定第一个垂直并做出端到端可演示闭环。
2. 把意图、协商、审计做成不可或缺而非附加功能。
3. 与 2–3 家打样/小批量伙伴建立真实连接。
4. 用试点数据验证节省与付费意愿。
