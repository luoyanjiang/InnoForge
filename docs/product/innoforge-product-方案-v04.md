## 0. 用户给定正（本方案必须服从）

1. **任务在项目内**：任务树是项目的执行层，随项目生命周期走。  
2. **个人任务 = 视图**：个人侧看到的任务是「我在各项目中被分配 / 负责的任务」的过滤视图，**不是**独立于项目的任务系统或并列「任务空间」。  
3. **流程纪律**：讨论文档 → **产品方案** → UI 设计 → 技术设计 → 开发；禁止跳过产品层直接改界面。

## 1. 产品定位

### 1.1 一句话

**InnoForge** 是创造流程的操作系统：把模糊意图变成可对齐的目标树、可调度的项目任务、可验证的闭环，以及可沉淀复利的资产网络；大模型只是能力层，壁垒在流程、协作协议与资产积累。

### 1.2 卖什么 / 不卖什么

| 卖 | 不卖（非目标） |
|----|----------------|
| 意图对齐与版本化目标树 | 通用大模型本身的性能竞赛 |
| 多主体协作协议（人-人 / 人-机 / 机-机） | 又一个「聊天式项目空间」 |
| 项目内任务树 → 验证 → 回流 | 独立的个人待办 / 工单产品 |
| 可组合资产 + 个人/团队/项目空间边界 | 一上来就做真钱市场与完整图谱库 |
| Credit / 声誉 /（远期）分成激励 | 用新经济叙事覆盖 Intent OS Credit 闭环 |
| 三场景共享底座、插件差异 | 拆成三个独立产品 |

### 1.3 与 Intent OS × InnoForge 的关系

- **Intent OS 闭环保留**：创建意图（质押）→ 孪生 / Agent 判断 → 人类确认 → 受控部署 → 反馈结算 → 权益 / 声誉。  
- **v0.4 叠加为同一产品的上层能力地图**：项目容器、意图树、项目任务树、空间权限、资产沉淀、场景插件 — **映射进闭环，不另起产品、不覆盖 Credit / 部署 / 治理**。  
- 现行原型中的「意图（intent）」在产品层升格为 **项目（Project）的主意图载体**（见 §2）；技术上可暂用 `forge_intents` 承载，但产品语义以项目为准。

## 2. 核心对象模型

### 2.1 对象一览

| 对象 | 定义 | 归属 |
|------|------|------|
| **Team** | 组织 / 协作单元；共享规范与团队资产库 | 租户下 |
| **Project** | **创造工作的主容器**：意图树 + 任务树 + 项目内临时资产 + 成员与权限 + 场景模式 | 属于 Team（或个人临时团队） |
| **Intent tree** | 项目内目标 / 约束 / 成功标准 / 分支的可版本化树 | **仅存在于 Project** |
| **Task tree** | 把假设 / 方案 / 验证路径拆成可调度工作单元（AI \| HUMAN \| 混合） | **仅存在于 Project**；可绑定意图树节点 |
| **Collab stage** | 项目级协作状态机（如 Draft → Exploring → Validating → Committed） | Project |
| **Space** | **权限与资产边界**，不是第二套任务系统：Personal / Team / Project | 见 §2.3 |
| **Asset** | 可沉淀组件、实验包、设计、失败案例等 | 产生于 Project；可沉淀到 Personal / Team / 公开市场 |
| **Contribution** | 细粒度动作与影响记录（任务执行、判断、资产、决策） | 贯穿 Project；汇总到个人声誉 |
| **Credit / 经济** | Intent OS 质押与结算 + 远期积分声誉 / 资产分成 | 不因 v0.4 被替换 |

### 2.2 关键关系（产品层）

```
Team
 └─ Project  ←—————— 主容器（随项目走）
      ├─ Intent tree     （对齐「做什么 / 为何 / 成功标准」）
      ├─ Task tree       （对齐「谁执行 / 做到哪 / 结果回流」）
      ├─ Collab stage + agents
      ├─ Project-space assets（草稿、中间结果）
      └─ Deploy / validate / feedback（接 Intent OS 确认·部署·结算）

Personal space
 └─ 私有资产 · 草稿 · 代理配置
 └─ 「我的任务」= Σ(各 Project 中 assigned-to-me 的任务)   ← 视图，非第二任务库

Team space
 └─ 已验证共享资产 · 模板 · 分配规则

Public market（远期）
 └─ 公开资产交易 / 引用分成
```

### 2.3 空间：权限与资产边界（不是任务空间）

讨论文档 §5.7：**个人 / 团队 / 项目空间是资产的组织与权限边界**。

| 空间 | 装什么 | 不装什么 |
|------|--------|----------|
| **Project space** | 本项目意图树、任务树、中间产物、实验数据；成员可见 | — |
| **Team space** | 团队验证过的组件、流程、模板、失败案例 | 独立任务队列 |
| **Personal space** | 私有草稿、未发布资产、个人代理配置、能力画像 | **独立任务系统** |

**「我的任务」**：产品入口可以存在（总览或个人空间附属），但语义是：

> 跨项目过滤视图：`WHERE assignee = me AND project.status ∈ active`

任务的创建、分解、依赖、完成、结果回流 **一律在所属 Project 内完成**。个人视图禁止成为可脱离项目的任务 CRUD 主路径。

### 2.4 意图树 vs 任务树

| | Intent tree | Task tree |
|--|-------------|-----------|
| 回答 | 目标对齐了吗？约束/成功标准是什么？ | 谁去做？做到哪一步？产出是什么？ |
| 节点例 | GOAL / CONSTRAINT / SUCCESS / BRANCH（假设或方案） | 验证步骤、原型、实验、仿真、打样、评审 |
| 绑定 | — | 任务可绑定意图节点（尤其 BRANCH / SUCCESS） |
| 回流 | 验证结果更新节点状态 / 置信度 | 任务 DONE/FAILED 触发回流与下游任务 |

### 2.5 与 Intent OS 对象的映射（整合，不覆盖）

| Intent OS / 现行 InnoForge | 产品方案中的位置 |
|----------------------------|------------------|
| Intent + stake / Credit | Project 创建与资源承诺；Credit 账本不变 |
| Constraints / freeze | Intent tree 的 CONSTRAINT + 冻结规则 |
| Twin / Agent variants / judgments (G2) | 工作台确认层；判断写入责任链与贡献 |
| Confirm → Deploy → Feedback → Settle | 项目验证与物理执行出口；阶段 Committed ≠ 已部署 |
| Snapshots / governance (G6) | 项目版本与回滚 |
| Lifeforms (G7) | 结算后可选演化；仍挂在项目脉络 |
| Lumen memories (G8) | 个人/项目记忆；可沉淀为资产候选 |
| Reputation / allocations (G4/G5) | 贡献出口；任务执行为新增贡献源 |
| Marketplace / adapters | 资产复用与外部能力；接 Team / Public |

## 3. 三场景产品差异（共享底座，不拆产品）

共享：**Project 容器、意图树、任务树、协作协议、Credit/贡献、空间权限、部署网关**。  
差异：默认意图模板、协作阶段文案、代理角色侧重、任务类型、验证形态、插件入口。

| | 产品创新 PRODUCT | 科研 RESEARCH | 硬件 HARDWARE |
|--|------------------|---------------|---------------|
| **项目焦点** | 商业目标 / 用户问题 / 增长 | 假设 / 证据 / 可证伪 | 约束优先 / 仿真 / 打样 |
| **意图树侧重** | 目标·用户问题·成本合规时间 | 假设·证据·空白 | 功能·工艺·BOM·合规 |
| **协作阶段（产品文案例）** | 定义→原型→实现→验证 | 假设→设计→实验→分析 | 约束→设计→仿真→打样 |
| **任务树典型分支** | 多验证方案并行（交互/定价） | 每假设一棵验证树 | 仿真批次 / 询价 / 打样 |
| **验证** | 原型 + 用户或模拟用户 | 可复现实验流水线 | 仿真-实测偏差闭环 |
| **插件（产品能力，非已实现）** | 原型 / 增长模拟 | 文献图谱 / 实验设计 | FreeCAD·OpenFOAM 等编排 |
| **切入** | 首突破口（SaaS 等垂直） | 第二曲线 | 子领域（如小批量结构件）后再加重 |

场景是 **Project 属性**（可会话预览覆盖文案），不是三个 App。

## 4. 产品信息架构（流程，非像素）

### 4.1 主流程（创造闭环）

```
创建 / 加入 Project（场景 · 成员 · Credit 质押若需要）
  → 对齐 Intent tree（多人分支 · 冲突提示 · 版本）
  → 协作阶段推进（代理在场 · 关键人类确认）
  → 在 Project 内展开 Task tree（绑定意图节点 · 分配 AI|人）
  → 执行与评审 → 结果回流意图树 / 假设置信度
  → 验证出口：确认调度 · 部署 · 反馈 ·（可选）生命体
  → 里程碑：资产沉淀提示 → Personal / Team /（远期）市场
  → 贡献计量 → Credit 结算 / 声誉 /（远期）分成
```

### 4.2 导航语义（产品层 IA — 纠正 F1）

产品层应以 **Project 为中心**，而不是「顶层并列任务空间 + 顶层并列资产三栏」：

| 区域 | 产品含义 | 正确 / 错误 |
|------|----------|-------------|
| 项目上下文壳 | 当前 Project：意图树 · 协作 · **项目任务** · 工作台 · 部署 | ✅ 任务在此 |
| 发现 / 项目列表 | 进入或创建 Project | ✅ |
| 个人「我的任务」 | 跨项目 assignment 视图 | ✅ 仅视图 |
| 个人 / 团队空间 | 资产与权限 | ✅ 非任务库 |
| **顶层并列「任务执行」与「资产空间」对等、暗示独立任务空间** | F1 壳层产品表述 | ❌ **产品错误，须在后续 UI 设计废止** |

### 4.3 空间流转（产品）

`个人草稿 → 项目内使用 → 里程碑沉淀到团队 → 可选公开市场`  
反向：`市场 / 团队资产 → 引用进项目（记版本与依赖）`。

## 7. F1 产品错误（显式废止）

F1 实现把侧栏做成对等分组「任务执行 | 资产空间」，并提供顶层 Tasks / Spaces 页，容易读成：

- 存在与项目平级的「任务空间」；  
- 个人 / 团队 / 项目是并列任务或工作区，而非 **资产权限边界**；  
- 「我的任务」可以脱离项目存在。

**废止结论（产品层）：**

1. 不存在独立的「任务空间」产品概念。  
2. Task tree **只**属于 Project；随项目归档/生命周期。  
3. Personal「任务」= 跨项目 assignments 视图。  
4. Spaces = 资产与权限；Project space 与 Project 容器同体，不是第四套任务箱。  
5. 后续 UI 设计必须以 Project 为导航中心重排 IA；F1 代码可暂留，但不得再按错误模型扩展产品叙事。

详见 [fidelity plan · F1 纠错](./innoforge-v04-ui-fidelity-plan.md)。

## 8. 附录：UI 设计含义（短 · 非完整 UI 设计）

用户批准本方案后，再开正式 UI 设计文档。此刻仅锁定含义：

1. **项目壳优先**：进入产品后先选/建 Project；意图树与项目任务是项目内主舞台。  
2. **收回顶层「任务」并列感**：项目内「任务」一级；全局仅保留「我的任务」视图入口。  
3. **空间入口**：强调沉淀 / 引用 / 权限；避免三栏看起来像三个任务看板。  
4. **场景**：切换改变项目工作区文案、默认任务种子与插件 hint，不换 App。  
5. **保留 Intent OS 路径**：创建质押、工作台判断、确认部署、治理权益必须仍可达。  
6. **zh / en 不混排**；诚实标注 sim（无假图谱 / 假真钱）。
